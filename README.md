# Glossa — двунаправленный перевод русского жестового языка

Система перевода **русского жестового языка (РЖЯ)** в реальном времени: с
камеры/загруженного видео — в русский текст и озвучку, и обратно — из
текста/речи — в последовательность жестов (видео эталонных клипов или
skeleton-анимация). Поддерживается режим двустороннего видеозвонка между
двумя участниками. Дипломный проект.

   │ rtmlib  │    │ Qwen2-  │    │ Silero  │    │ faster- │

![Общая архитектура](docs/img/1.%20%D0%9E%D0%B1%D1%89%D0%B0%D1%8F%20%D0%B0%D1%80%D1%85%D0%B8%D1%82%D0%B5%D0%BA%D1%82%D1%83%D1%80%D0%B0.png)

**РЖЯ → Текст:** камера/видео → CV (skeleton → автоматическая сегментация
жеста по амплитуде движения → ST-GCN классификатор, top-3) → буфер
предложения → NLP (T9-подобная дизамбигуация последовательности жестов с
учётом контекста диалога → русское предложение) → TTS (озвучка).

![Пайплайн РЖЯ → Текст](docs/img/2.%20%D0%9F%D0%B0%D0%B9%D0%BF%D0%BB%D0%B0%D0%B9%D0%BD%20%D0%A0%D0%96%D0%AF%20%E2%86%92%20%D0%A2%D0%B5%D0%BA%D1%81%D1%82.png)

**Текст → РЖЯ:** текст или голос (→ ASR) → NLP (перевод, строго
ограниченный реальным 200-словным словарём жестов — детерминированный
пост-фильтр отбрасывает всё, чего нет в словаре) → TTS (склейка эталонных
видео-клипов или skeleton-анимация для вывода клиенту).

![Пайплайн Текст → РЖЯ](docs/img/3.%20%D0%9F%D0%B0%D0%B9%D0%BF%D0%BB%D0%B0%D0%B9%D0%BD%20%D0%A2%D0%B5%D0%BA%D1%81%D1%82%20%E2%86%92%20%D0%A0%D0%96%D0%AF.png)

**Двусторонний звонок:** два участника привязываются друг к другу по
короткому коду; финальный перевод каждой стороны транслируется другой в
реальном времени поверх тех же двух однонаправленных пайплайнов.

![Relay двустороннего звонка](docs/img/6.%20Relay%20%D0%B4%D0%B2%D1%83%D1%81%D1%82%D0%BE%D1%80%D0%BE%D0%BD%D0%BD%D0%B5%D0%B3%D0%BE%20%D0%B7%D0%B2%D0%BE%D0%BD%D0%BA%D0%B0.png)

GPU-развёртывание (`docker-compose.gpu.yml`) поддержано для всех четырёх
ML-сервисов (CV/NLP/TTS/ASR) и подтверждено на реальном VM-стенде — даёт
кратный выигрыш в задержке относительно CPU (например, обратный перевод
текст→жесты: ~20 c на CPU → ~1.5–2 c на GPU).

## Быстрый старт

```bash
# 1. Клонировать репозиторий и настроить окружение
git clone https://github.com/noviyblock/glossa.git && cd glossa
cp .env.example .env

# 2. Скачать модели и датасет
make models          # модели с Google Drive
dvc pull              # или через DVC/DagsHub — модели + data/idx_to_class.json

# 3. Запустить (CPU)
make dev              # горячая перезагрузка (docker-compose.override.yml)
# make up              # фоновый режим

# 3'. Или на GPU-хосте (CV/NLP/TTS/ASR на CUDA):
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build

# 4. Открыть интерфейсы
open http://localhost:8000/docs   # Swagger / ReDoc
open http://localhost:5000        # MLflow — эксперименты
open http://localhost:3001        # Grafana  (admin / admin)
open http://localhost:9090        # Prometheus
```

## Сервисы

| Сервис          | Порт | Технология                                   | Возможности                                                                                     |
|-----------------|------|-----------------------------------------------|---------------------------------------------------------------------------------------------------|
| `api-gateway`   | 8000 | FastAPI + WebSocket                           | Точка входа, буферизация и накопление предложения из нескольких жестов, общая для обоих направлений история диалога, изоляция состояния между сессиями/режимами, relay для видеозвонка |
| `cv-service`    | 8001 | rtmlib (RTMDet+RTMPose) + ST-GCN (ONNX/OpenVINO) | Извлечение skeleton (тело + обе кисти), автоматическая сегментация непрерывного видео на отдельные жесты (state machine по амплитуде движения, без ручной кнопки), классификация (200 классов, top-3, TTA), устойчивость к кратковременной потере трекинга рук |
| `nlp-service`   | 8003 | Qwen2-1.5B, LoRA-дообучение, 4-bit inference  | Дизамбигуация последовательности распознанных жестов в связное русское предложение с учётом контекста; обратный перевод текста в жесты, строго ограниченный реальным словарём (RAG-lite: лексический предфильтр кандидатов + few-shot + детерминированный пост-фильтр) |
| `tts-service`   | 8004 | Silero TTS + сборка видео/skeleton            | Озвучка распознанного текста; сборка клипа из эталонных видео на каждую глоссу (ffmpeg) либо покадровая skeleton-анимация — без необходимости иметь видео на каждое слово |
| `asr-service`   | 8002 | faster-whisper                                | Голосовой ввод для слышащего собеседника (альтернатива печати текста)                             |
| `redis`         | 6379 | Redis 7.2                                     | Состояние сессий, очереди результатов, пары звонков                                               |
| `mlflow`        | 5000 | MLflow + SQLite                               | Трекинг экспериментов                                                                             |
| `prometheus`    | 9090 | Prometheus                                    | Сбор метрик всех сервисов                                                                         |
| `grafana`       | 3001 | Grafana                                       | Дашборды                                                                                           |

## Реальные показатели (боевое развёртывание)

В отличие от dry-run-оценок ниже (раздел «Эксперименты» — там числа
изначально были архитектурными прикидками, не измерениями, см.
пояснение в том разделе), здесь — числа, подтверждённые реальными
прогонами: либо на held-out валидации реальной моделью, либо на боевом
VM-стенде с реальными пользовательскими сессиями.

**Качество классификатора не бралось из одного прогона — три
последовательных, реально обученных и измеренных стадии:**

![Прогресс accuracy по стадиям обучения](docs/img/M1.%20%D0%9F%D1%80%D0%BE%D0%B3%D1%80%D0%B5%D1%81%D1%81%20accuracy%20%D0%BF%D0%BE%20%D1%81%D1%82%D0%B0%D0%B4%D0%B8%D1%8F%D0%BC%20%D0%BE%D0%B1%D1%83%D1%87%D0%B5%D0%BD%D0%B8%D1%8F.png)

1. **Baseline (47.7%)** — без подбора гиперпараметров, статическая аугментация.
2. **После Optuna-подбора гиперпараметров + аугментации на лету (61.4%)**.
3. **После дообучения на keypoints из боевого экстрактора (82.0%)** — офлайн-обучение шло на DWPose-извлечённых точках, а в проде кадры извлекает rtmlib/RTMW; между ними реальный домен-гэп (разное поведение при окклюзии/низкой уверенности), и third-stage дообучение его закрывает. Это сейчас реально задеплоенная модель (проверено по дате файлов и порядку загрузки бэкендов в `gesture_classifier.py` — OpenVINO грузится первым, `models/stgcn_topk_int8/` перезаписан именно на этой стадии).

**Test-Time Augmentation — измеренный результат, не предположение:**

![TTA — точность против задержки](docs/img/M2.%20TTA%20%E2%80%94%20%D1%82%D0%BE%D1%87%D0%BD%D0%BE%D1%81%D1%82%D1%8C%20%D0%BF%D1%80%D0%BE%D1%82%D0%B8%D0%B2%20%D0%B7%D0%B0%D0%B4%D0%B5%D1%80%D0%B6%D0%BA%D0%B8.png)

На чистом held-out val (n=1000) TTA не даёт прироста точности (62.8%→62.7%,
разница в пределах шума), но стоит 3× по задержке (47.2мс→142.1мс) — честно
измеренный отрицательный результат, включён как есть, а не спрятан.

**rtmlib: lightweight vs balanced — реальный A/B со статистикой:**

![rtmlib lightweight vs balanced](docs/img/M3.%20rtmlib%20lightweight%20vs%20balanced.png)

n=185 реальных клипов, 95% доверительные интервалы пересекаются — разница
в точности статистически не значима, при этом `balanced` в 3.26× медленнее.
Вывод: остаёмся на `lightweight` (подробности — `RTMLIB_MODE_BENCHMARK.md`).

## WebSocket API

```
ws://localhost:8000/api/v1/ws/translate/{mode}
```

`mode`: `rsl_to_text` | `text_to_rsl`

**Клиент → сервер:**
```json
{"type": "video_frame",         "frame": "<base64 JPEG>",  "session_id": "<uuid>"}
{"type": "audio_chunk",         "audio": "<base64 PCM>",   "session_id": "<uuid>"}
{"type": "flush_sentence",      "session_id": "<uuid>"}
{"type": "delete_last_gesture", "session_id": "<uuid>"}
{"type": "end_session",         "session_id": "<uuid>"}
```

**Сервер → клиент:**
```json
{"type": "gloss",            "payload": {"glosses": [...], "gesture_active": true, "preview": false}}
{"type": "pending_sentence",  "payload": {"positions": [...]}}
{"type": "chunk",             "payload": {"text": "...", "is_final": false}}
{"type": "result",            "payload": {"text": "..."}}
{"type": "audio",             "payload": {"wav": "<base64 WAV>"}}
{"type": "video",             "payload": {"video": "<base64 MP4>"}}
{"type": "skeleton",          "payload": {"sequences": [...]}}
{"type": "peer_message",      "payload": {...}}
{"type": "error",             "payload": {"message": "..."}}
```

REST: `POST /api/v1/translate` (text_to_rsl без WS), `POST /api/v1/asr`
(речь → текст → тот же путь text_to_rsl), `POST /api/v1/call/create`,
`POST /api/v1/call/{call_id}/join` (двусторонний звонок).

## CI/CD и качество

GitHub Actions, четыре независимых workflow:

- **`ci.yml`** — lint (ruff/black/mypy), security lint (bandit), тестовый
  прогон (`pytest libs/ services/` с покрытием), матричная сборка и
  публикация Docker-образов всех пяти сервисов в GHCR.
- **`security.yml`** — CodeQL SAST, Bandit SAST, Trivy (сканирование
  файловой системы и собранных образов), dependency review, TruffleHog
  (поиск утечек секретов).
- **`cd.yml`** — деплой.
- **`mlops.yml`** — проверки ML-пайплайна.

Каждый сервис — многостадийный Docker-образ с отдельными CPU- и
GPU-таргетами (`production` / `production-gpu`).

## Эксперименты

Каждый эксперимент под `experiments/NN_*/run.py --dry-run` обосновывает
решение по выбору архитектуры **на уровне оценки архитектурных
характеристик**, без GPU. Важно понимать, что это такое: числа в
`experiments/*/results.json` — заранее заданные (hardcoded) оценки для
dry-run режима, не результат реального обучения/инференса на этих
данных (это явно видно в самом коде — например,
`experiments/03_inference_acceleration/run.py` буквально комментирует
`# Simulated results for dry-run`). Не путать с реальными измерениями
разделом выше — там числа получены прогоном настоящей модели.

```bash
make exp-dry      # все 9 экспериментов в dry-run — архитектурные оценки, не измерения

# Или по одному:
python experiments/01_gesture_backbone/run.py --dry-run
python experiments/08_e2e_latency/run.py --dry-run
```

Реальные измерения — не `dvc repro` (проверено: у `dvc.yaml`'s
`preprocess`/`train_gesture`/`eval_gesture` сейчас несогласованные пути
между стадиями, `dvc repro` на них ломается — известная проблема,
исправление в работе), а конкретные скрипты и отчёты:
`scripts/measure_accuracy.py` (гоняет настоящие модули `cv_service` на
реальных клипах), `RTMLIB_MODE_BENCHMARK.md`, `notebooks/colab_glossa_01a_train_stgcn_64_200.ipynb`
и `notebooks/colab_glossa_04_finetune_rtmw.ipynb` (см. таблицу ноутбуков ниже).

| №  | Эксперимент                           | Вопрос                                          |

## Данные и предобработка

Датасет — [Slovo](https://github.com/hukenovs/slovo) (русский жестовый
язык), из него отобрано 200 наиболее различимых по жестам классов
(`data/selected_classes_200.json`) — сознательное сужение объёма для
MVP, полный ~1000-классовый корпус тоже прогонялся отдельно (пайплайн
проверен, см. «Дальнейшее развитие»).

Реальный путь одного клипа от видео до входа модели:

1. **Извлечение keypoints** — DWPose офлайн (обучение) / rtmlib-RTMW в
   проде (инференс), 75 точек: тело (33, с паддингом ключевых суставов),
   левая и правая кисть (по 21).
2. **Фильтрация по уверенности** — точки тела с `confidence < 0.3`
   обнуляются; для кистей порог отдельный и ниже, `confidence < 0.15`
   (руки — основной сигнал жеста, RTMW никогда не возвращает честное
   "не вижу", поэтому для них терпимость к шуму выше — `services/cv_service/config.py`).
3. **Нормализация** — центрирование по центру бёдер, масштаб по
   расстоянию между плечами (инвариантность к росту/дистанции до
   камеры), клип `[-10, 10]`, затем z-score по среднему/std обучающей
   выборки (`models/norm_stats.npz`).
4. **Приведение к единому окну** — 64 кадра, **линейной
   передискретизацией** (`np.linspace` + линейная интерполяция между
   соседними кадрами, `services/cv_service/sliding_window.py::_resample_to`) —
   не DTW, несмотря на что можно было бы предположить для
   time-series-задачи; DTW в проекте не используется нигде.
5. **Аугментации при обучении** (только train, `AugmentedGestureDataset`
   в `colab_glossa_01a`):

   | Аугментация | Вероятность | Параметры |
   |---|---|---|
   | horizontal_flip (зеркалирование + перестановка L/R) | 0.5 | — |
   | spatial_jitter (гауссов шум) | 0.5 | σ=0.02 |
   | temporal_warp (изменение скорости) | 0.3 | до ±15% |
   | hand_rotation (поворот кистей) | 0.3 | до 8° |
   | temporal_shift (сдвиг по времени) | 0.3 | до 8% длины |
   | random_scaling | 0.3 | до ±8% |
   | cutout_nodes (обнуление случайных суставов) | 0.15 | 3 узла |

6. **Test-time augmentation** (инференс, финальные — не preview —
   классификации): 3 варианта с тем же σ=0.02 джиттером, что и
   тренировочная `spatial_jitter` — усреднение softmax. Реальный эффект
   измерен и оказался отрицательным по стоимости (см. график выше) —
   решение оставить включённым принято осознанно, а не по умолчанию:
   на живом зашумлённом видео (не чистый val) усреднение может вести
   себя иначе, чем на чистых клипах, вопрос остаётся открытым.

**Валидация результатов не заканчивается на accuracy.** По confusion
matrix реального инференса (200×200, held-out val) найден и объединён
настоящий дубликат класса — `весёлый`/`веселый` (оба f1=0.000, взаимно
путаются) — орфографический вариант одного слова, не два разных жеста;
похожая по написанию пара `все`/`всё` **не объединена**, потому что
данные показали обратное: модель различает их надёжно (f1=0.667/0.667,
0 взаимных ошибок) — решение принято по измерению, а не по интуиции.
Порог уверенности классификации на живых сессиях тоже пересматривался
по факту: жёсткий фиксированный порог 0.35 отсекал не только шум между
жестами (ради чего его поднимали), но и часть настоящих распознаваний с
низкой, но единственно возможной уверенностью — типично для 200-классовой
задачи, где даже верный топ-1 не всегда доминирует в распределении.
Порог заменён на комбинацию абсолютного минимума и разрыва с ближайшим
конкурентом.

## Продукт

**Проблема.** Русским жестовым языком как основным языком общения в
России пользуются десятки-сотни тысяч человек, а более широкая
аудитория людей с нарушениями слуха — на порядок больше. Штатный
переводчик РЖЯ есть не в каждом учреждении и не в каждый момент
времени, видео-релей сервисы требуют стороннего посредника и
предварительной записи.

**Целевая аудитория:** (1) глухие/слабослышащие пользователи РЖЯ, (2)
слышащие собеседники — родственники, медицинский и социальный персонал,
операторы приёма граждан, (3) институции (поликлиники, МФЦ,
контакт-центры) как канал системного, а не разового внедрения.

**Альтернативы и позиционирование:** штатный переводчик-человек
(ограничен по доступности и расписанию), видео-релей сервисы (нужен
сторонний посредник), академические прототипы распознавания жестов (как
правило, не доведены до работающего в реальном времени продукта),
обычные переводчики текста (жестовый язык не поддерживают вовсе). Glossa
переводит в обе стороны, в реальном времени, с обычной веб-камеры в
браузере, без специализированного оборудования и без обязательного
участия человека-посредника.

**MVP реализован полностью:** оба направления перевода, распознавание с
камеры и с загруженного видео, голосовой и текстовый ввод для слышащей
стороны, режим двустороннего звонка.

**Импакт:** не замена переводчика в сложных/юридически значимых
ситуациях, а снятие барьера в рутинных коротких взаимодействиях, где
переводчика физически нет, и рост бытовой автономности пользователя РЖЯ.

## Применение ИИ в разработке

AI-агенты использовались на протяжении всего цикла разработки, не только
для автодополнения кода. Основной паттерн — итеративная отладка напрямую
по реальным логам с боевого VM-стенда: агент анализировал сырые логи
сервисов (задержки, confusion matrix, состояние конечного автомата
сегментации), формулировал гипотезу о первопричине по конкретным данным
(а не по общим соображениям), вносил точечное исправление и добавлял
регрессионный тест на именно этот найденный случай. Так же написана
часть офлайн-скриптов оценки качества, тестового покрытия и
документации (включая эту).
