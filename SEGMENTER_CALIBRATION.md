# GestureSegmenter threshold calibration

Дата: 2026-07-18. Не добавлен в git.

## Резюме

**Основной вопрос задачи (коррелирует ли неверная классификация с
аномальным segment_len) не удалось проверить** — нет контролируемого
прогона с известным порядком/скоростью жестов (тот же блокер, что и в
предыдущей задаче про class collapse). Единственный реальный лог,
доступный в этой сессии (`cv_service_cpu.log`, scratchpad, 5 жестов, без
ground truth), не даёт этого сделать и по диапазону (segment_len 20-31)
не совпадает с описанным в задаче (19-150+) — значит, вы смотрели на
другие, более длинные логи, которых у меня нет.

**Новая находка, важная сама по себе**: даже когда ground truth появится,
текущая гранулярность `DIAG`-лога (раз в 30 кадров, `main.py:208`)
недостаточна для запрошенного в п.3 подхода — "на основе распределения
last_activity". На единственном реальном логе episodes длиной 20-31 кадр
дают в среднем **0.8 DIAG-сэмпла на эпизод** — то есть чаще всего 0 или 1
точка `last_activity` на весь жест. Распределение из 0-1 точек — не
распределение. Это подтверждено скриптом (см. ниже), не предположение.

**Что сделано в этой задаче:**
1. `DIAG_LOG_INTERVAL` вынесен в `config.py` (был хардкод `% 30` в
   `main.py:208`) — дефолт не изменён (по-прежнему 30, поведение классификации
   не тронуто), но теперь для калибровочного прогона можно выставить
   `DIAG_LOG_INTERVAL=1` и получить last_activity на каждом кадре.
2. Написан `scripts/analyze_segmenter_calibration.py` — парсит лог в
   "эпизоды" (`IDLE->ACTIVE` … `ACTIVE->IDLE`, с учётом force-flush
   внутри одного эпизода), считает segment_len/force-flush count/
   last_activity-сэмплы, и, если дать `--ground-truth order,gloss,speed`
   CSV, строит именно ту таблицу (жест/скорость/segment_len/verdict),
   которую просит задача. Если число эпизодов не совпадает с числом строк
   ground truth — скрипт **отказывается угадывать** выравнивание и прямо
   об этом пишет, а не молча съезжает на одну позицию.
3. Скрипт прогнан (`py_compile` + реальный запуск) на единственном
   доступном логе в режиме без ground truth — работает, ниже реальный
   вывод.

## Предварительный (не окончательный) взгляд на n=5 без ground truth

```
  # session     seg_len  ff  discarded pred                  conf  activity samples (value@offset_streak)
  1 3569ff0f         31   0      False Витамин               0.23  0.0098@3
  2 3569ff0f         22   0      False временный             0.13  0.0292@3
  3 3569ff0f         30   0      False временный             0.15  0.1471@0
  4 3569ff0f         20   0      False временный             0.14  0.0099@5
  5 3569ff0f         23   0      False временный             0.14  (none captured)

segment_len: min=20 max=31 mean=25.2
```

Не могу сказать, сколько из этих 5 предсказаний верны — нет ground truth
для этого конкретного лога (какой жест реально показывался в каждый
момент, неизвестно). Что видно чисто механически:
- Ни одного force-flush (`ff=0` везде) — на этих 5 показах
  `GESTURE_OFFSET_THRESHOLD`/`GESTURE_OFFSET_FRAMES` срабатывали
  нормально, не упирались в `GESTURE_MAX_FRAMES=150`. Упомянутые в задаче
  сегменты 150+ в этом логе не встречаются — они из другого прогона.
   - 4 из 5 предсказаний — `"временный"` — это тот же паттерн class
   collapse, что уже задокументирован в `DIAGNOSIS_CLASS_COLLAPSE.md`, не
   новая находка, просто ещё одно подтверждение на новых данных.

Строить рекомендацию по threshold'ам на этом — нельзя: n=5, без ground
truth, без force-flush случаев (то есть без единого примера того самого
"слишком длинный сегмент", который в задаче называется подозреваемым).

## Что нужно от вас для реального ответа на задачу

1. **Контролируемый прогон**, как и раньше: заранее зафиксированный
   порядок из 15-20+ жестов, специально с разной скоростью исполнения
   (быстро/нормально/медленно, пометьте какой заход к какой скорости
   относится).
2. **Перед прогоном** выставьте `DIAG_LOG_INTERVAL=1` (или 2-3) на
   cv-service только на время этого теста — иначе last_activity
   распределение снова будет из 0-1 точки на жест, и п.3 задачи опять
   останется без ответа. Верните обратно на 30 (или просто уберите
   переменную) после.
3. **CSV** в формате `order,gloss,speed` (пример — в docstring
   `scripts/analyze_segmenter_calibration.py`), порядок строк — порядок,
   в котором жесты реально показывались.
4. Полный `docker compose logs cv-service` за время прогона.

С этим я:
```
python scripts/analyze_segmenter_calibration.py cv-service.log --ground-truth ground_truth.csv
```
— получу таблицу жест/скорость/segment_len/verdict, распределение
segment_len по correct/incorrect/discarded, и (при `DIAG_LOG_INTERVAL=1`)
достаточно плотный last_activity ряд, чтобы содержательно сравнить
"явно завершённые" и "явно продолжающиеся" моменты — именно то, что
просит п.3 задачи.

Пункты 3-4 задачи (предложить новые threshold'ы с обоснованием, прогнать
их и сравнить accuracy до/после) **не выполнены** — не гадаю числа без
данных, которых нет. Если распределения из будущего прогона не покажут
чёткого разрыва между correct/incorrect по segment_len или по
last_activity на границе эпизода — отвечу прямо: "перекалибровка
threshold'ов не объясняет проблему", как и просит п.4, вместо того чтобы
менять `GESTURE_ONSET_THRESHOLD`/`GESTURE_OFFSET_THRESHOLD` без
доказанного эффекта.
